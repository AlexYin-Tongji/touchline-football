# 看台 Touchline · 产品需求文档

当前迭代为 V3，新增目标、功能与验收见 [V3.md](V3.md)。本文保留首版基础需求，更新以第三版文档及实际接口为准。

版本：MVP 1.0 · 2026-09-09  
交付形式：本地运行、单用户的中文网页应用。后端使用 Python / FastAPI / SQLite，前端使用 React。

## 1. 产品判断

**替球迷持续跟队，把值得知道的变化和比赛里值得观察的事情讲清楚。**

产品围绕一支用户关注的球队形成连续体验：平时跟进消息，赛前理解看点，赛后对照事实，再通过问答补足用户想知道的背景。首版优先服务没有时间持续刷多个来源、但愿意理解球队和比赛的球迷。

AI 的工作是识别变化、查找证据、解释意义、提出观察点和更新判断。赛程、名单、比分以及消息内容必须来自已导入资料或已启用来源。AI 不负责创造这些事实。引用核验至少检查证据编号属于当前资料集、引用指向原文；界面始终区分来源事实与模型解释。

用户可以把“继续跟进这件事”交给应用。服务运行时，应用按已启用来源的采集间隔更新资料；用户请求解读时，简洁的 Agent 循环从本地资料中检索、阅读、比较，再带证据作答。首版不承诺电脑关闭后的持续任务。

## 2. 设计原则与技术边界

1. **自己实现工具和技能。** 消息采集、正文提取、本地搜索、证据读取、事件比较和比赛上下文读取均为仓库内实现。技能采用可读、可修改的本地文件，明确目标、使用顺序、证据要求和停止条件。
2. **不接入第三方足球分析、预测或搜索 API。** 外部资料通过我们实现的 RSS/HTML 采集器取得，也支持手动导入。唯一必须允许的外部推理能力是用户自行配置的 LLM 服务；首版支持 OpenAI compatible 接口。
3. **Harness 从简。** 自研一个有轮次、时间、工具白名单和取消边界的循环；可借鉴开源框架的消息与工具协议，不引入复杂编排平台、多 Agent 网络或额外运行服务。
4. **证据先于解释。** 对缺失事实明确标注“资料不足”。出现矛盾时展示来源和时间差异，不把多次转载当作多条独立证据。
5. **少打扰。** 展示新的、有意义的内容，保留已读状态。没有更新时展示“暂无新变化”。
6. **球迷优先。** 主界面面向跟队和看球；模型、来源与执行限制放在设置或详情中。AI 的执行步骤可展开核查，默认不占据主阅读区域。

## 3. 用户与关键任务

| 用户故事 | 完成标准 |
| --- | --- |
| 我几天没有关注球队，想迅速跟上 | 首页集中展示尚未读过的消息，带主题、来源和时间；能够标记已读并查看全部资料 |
| 我看到相互矛盾的传闻，想知道现在能确认什么 | 问答引用对应原文，区分已确认内容、相互冲突的说法和缺失证据；不擅自下结论 |
| 我想在下一场比赛前知道应该看什么 | 比赛中心基于现有资料给出有限的观察点、依据和可观察的现象；无资料时给导入入口 |
| 我想知道赛前判断有没有发生 | 赛后复盘根据已有赛后资料对照观察点，标注支持、相反或无法核验 |
| 我想把某条球队新闻继续跟下去 | 能关注或取消关注对应事件，首页可筛选关注内容；新关联资料进入该事件的进展 |
| 我已有自己的模型，希望直接使用 | 在设置填写服务地址、模型与密钥，保存并测试连接；得到明确成功或失败信息 |
| 我想只使用我信任的资料 | 能添加、启停、手动刷新 RSS/HTML 来源，也能直接粘贴资料；看到上次采集结果和错误 |
| 我稍后才看录像，不想被剧透 | 避剧透开启后，首页、比赛卡和推荐问题不主动展示比分、赛果或赛后内容；进入复盘前明确揭示操作 |

## 4. 首版范围与功能优先级

### P0：必须完成

| 模块 | 功能设计 | 验收要求 |
| --- | --- | --- |
| 应用框架 | 五个页面：球队动态、比赛中心、跟队问答、资料来源、设置；关注球队统一使用全局设置 | 桌面侧栏与移动导航均可到达全部页面；切页不丢失已保存配置 |
| 模式隔离 | 顶层明确区分演示资料与真实资料 | 演示内容持续有“虚构示例”标记；真实模式搜索、信息流和回答绝不读取演示资料；首次真实模式为可信的空状态 |
| 球队动态 | 消息列表、主题/事件、重要性提示、日期、来源、已读、关注事件、全部/未读/关注筛选 | 同一来源相同内容不重复入库；读后状态持久化；详情能追到证据原文 |
| 比赛中心 | 下一场/已结束比赛卡，赛前观察与赛后复盘；展示比赛基本信息的出处 | 没有比赛资料时不生成对阵、时间或比分；演示场景可完整体验；真实内容仅使用资料支持的信息 |
| 跟队问答 | 输入问题、推荐问题、生成结果、证据列表、可展开执行步骤、停止按钮、重试 | 完成一次有限循环；每条证据可打开其原文；取消后结果标记为已取消且不继续调用模型 |
| 资料来源 | 自研 RSS/HTML 抓取；添加、启停、删除来源；单次采集、采集状态；手动文本导入 | 来源失败可定位；无外部足球/搜索 API；导入可填写标题、URL、发布时间、主题及比赛相关信息；无原始 URL 的资料标明“手动导入” |
| 定时采集 | 服务运行期间轮询已启用来源 | 明示只在服务运行时有效；启停开关和采集间隔生效；单个来源失败不阻塞其它来源 |
| 模型配置 | 服务地址、模型名、API 密钥；保存、连接测试、状态提示 | 保存后刷新可用；浏览器回读只得到是否配置的标记；测试不得误报成功；没有配置模型时提示配置入口 |
| Agent 配置 | 最大轮次、单次请求/任务超时等有界参数 | 参数在后端验证；超限任务返回可读停止原因；输出已有证据和可用的部分结果 |
| 用户偏好 | 关注球队、避剧透、解释深度 | 持久化并用于后续页面和问答；解释深度改变表述细节，不能改变事实判断 |
| 可运行交付 | 本地存储、启动说明、示例资料、关键自动验证 | 新环境依说明可启动；可完整走通示例流程；模型失败、采集失败和无资料均有明确状态 |

### P1：后续增强

- 更可靠的原始来源识别、转载聚类和事件自动归并。
- 赛前观察点与赛后证据逐项结构化对照。
- 多支球队的不同通知偏好，以及浏览器通知。
- 用户反馈对消息重要性排序的持续校准。
- 更细的球员、阵容和比赛时间线模型，以及更丰富的正文提取适配器。
- 可编辑技能的可视化管理与版本比较。

### 本轮不包含

实时直播、自动视频分析、没有数据支持的战术跑位分析、赔率/投注/胜率预测、自动代发社交内容、付费订阅、多人账号、复杂权限体系、云端部署和高可用调度。完整的比赛事件数据、阵容数据库和版权视频由后续合法数据源建设决定。

## 5. 页面功能与主流程

### 5.1 首次进入

首次进入可查看虚构示例，界面持续提醒当前数据性质。切换到真实资料后，先设置关注球队、导入一份资料或配置一个来源，再配置模型开展问答。导入和阅读资料不依赖模型可用。任何没有完成的设置都以就近入口提示，不用阻断式向导锁住应用。

### 5.2 球队动态

- 顶部呈现关注球队、模式、下一场比赛摘要或“尚无比赛资料”。
- 变化卡的阅读顺序是标题、内容摘要、事件标签、来源与时间，再到“关注”和“已读”。
- 点击卡片打开正文/证据详情，提供“问问这条消息”的上下文入口。
- 来源没有提供发布时间时显示“发布时间未知”，采集时间独立显示，禁止用采集时间冒充新闻时间。
- 对于尚未经模型解释的资料，清楚按来源消息呈现；不得把规则标签包装成经验证的足球分析。
- 内容重复检测首先使用规范化 URL 与正文哈希。跨来源相似文章的精确聚类作为增强，不在首版虚称已解决。

### 5.3 比赛中心

- 比赛卡展示对阵、开赛时间、比赛状态及来源。真实模式无数据时引导在导入中补充比赛资料。
- 赛前生成按钮调用赛前技能。结果包括已知背景、至多三个观察点、每点依据及资料缺口。
- 赛后复盘调用复盘技能。已有赛前观察时优先对照；缺乏赛后资料时说明无法核验，不补写比赛过程。
- 用户开启避剧透时，比分、结果、复盘正文默认隐藏。用户主动选择“揭示赛果并查看复盘”后才展示本场相关内容。

### 5.4 跟队问答

输入框允许围绕球队和现有资料自由追问。推荐问题随着页面上下文变化，例如“这条消息确认到什么程度？”“对下一场可能有什么影响？”“赛前看点有什么证据？”。

一次运行在界面上呈现三个层次：

1. **回答**：先给有依据的结论，区分事实、解释和仍需确认的内容。
2. **证据**：编号、标题、发布/采集时间、原文片段、原始链接。
3. **执行步骤**：显示选择的技能、工具名称、阶段和简短结果；不展示模型私有推理或密钥。

没有资料时，系统可以直接返回资料不足并引导导入。模型未配置、连接失败、取消、超限都独立呈现，不用成功样式包装错误。真实模式禁止自动降级为演示回答。

### 5.5 资料来源与导入

RSS 适合持续跟踪，HTML 适合已知文章页面，手动导入用于用户已有材料。采集器采用自研实现；第三方通用解析库可以使用，但采集、清洗、去重、入库与证据定位的业务逻辑属于本项目。

每个来源展示类型、URL、是否启用、上次尝试时间、上次成功时间、新增条数及错误。来源网页内容一律视为资料，不得让其内容改变系统指令、工具许可或密钥设置。采集限制内容大小、请求超时及协议，不允许任意本地文件读取。

手动导入最少需要标题和正文。可补充原文 URL、发布时间、标签、事件以及比赛信息。导入成功直接链接到资料详情；清洗后的原文保留，模型摘要不能覆盖原始证据。

### 5.6 设置

- 关注球队、解释深度、避剧透偏好。
- LLM：兼容接口基础地址、模型名称、密钥保存/更新/清除、连接测试。
- Harness：最大轮次、超时和当前可用工具/技能的只读清单。
- 采集：总开关和间隔，明确服务运行边界。

密钥仅由后端机密存储处理，不写入前端持久化存储、不进入 API 的读取响应、不输出到日志或执行轨迹、不提交到版本库。前端只能显示“已配置”或“未配置”；留空保存保持既有密钥，清除使用明确操作。测试连接使用当前已保存配置，结果带测试时间和可读原因。

## 6. 最小 Agent 架构

```text
用户任务 + 球队/模式/偏好
           ↓
选择本地 skill，建立有限任务
           ↓
LLM 决定下一步或给出回答
           ↓
执行白名单内的自研工具 → 记录工具结果 → 回到 LLM
           ↓
校验证据编号与模式 → 回答 + 来源 + 执行记录
```

首版建议工具职责：

| 工具职责 | 输入 / 输出 | 限制 |
| --- | --- | --- |
| 检索本地资料 | 关键词、球队、时间 → 资料摘要和证据 ID | 强制当前模式过滤，结果数量有界 |
| 阅读证据 | 证据 ID → 原文、来源、时间 | ID 必须来自当前模式；原文长度有界 |
| 读取比赛上下文 | 比赛 ID → 已导入比赛信息与关联资料 | 缺失字段显式为空 |
| 查看事件进展 | 事件标识 → 按时间排列的相关资料 | 不混淆采集时间与发布时间 |

技能最少覆盖“球队变化解读”“赛前观察”“赛后复盘”“证据问答”。技能文件可直接审阅并随代码版本管理。采集调度与模型循环分开：LLM 不得自行增加来源或修改运行配置。

达到最大轮次、超时或收到取消请求时停止；无效工具名、无效参数和未知证据 ID 产生显式错误。工具结果作为不可信资料交给模型，工具白名单由后端固定控制。首版输出验证可拦截无效引用，但不将引用存在等同于语义结论已被完全证明。

## 7. 状态与数据约定

| 对象 | 关键字段 | 状态 |
| --- | --- | --- |
| 用户设置 | 球队、解释深度、避剧透、模式 | 已保存 / 有未保存修改 |
| 来源 | 类型、URL、启用、采集时间、错误 | 未采集 / 采集中 / 正常 / 失败 / 已停用 |
| 资料 | 模式、标题、原文、URL、发布时间、采集时间、哈希、事件/比赛关联 | 未读 / 已读 |
| 关注事件 | 标识、名称、关联资料 | 已关注 / 未关注 |
| 比赛 | 模式、对阵、时间、状态、比分（可空）、来源 | 未开始 / 进行中 / 已结束 / 状态未知 |
| Agent 运行 | 模式、问题、技能、步骤、回答、引用、停止原因 | 等待 / 运行中 / 已完成 / 已取消 / 已失败 / 已超限 |
| 模型配置 | 服务地址、模型、机密引用、测试时间 | 未配置 / 未测试 / 可连接 / 测试失败 |

所有演示资料在存储层有独立模式标识。模式隔离作用于列表、检索、详情、比赛、问答和执行记录；不能仅靠前端隐藏。示例涉及的球队、人物、事件与比赛明确为虚构，示例来源不得伪装成真实新闻出处。

## 8. 核心验收场景

1. **演示闭环**：打开虚构示例 → 查看一条变化 → 关注事件并标记已读 → 比赛中心查看观察点 → 问答查看引用与工具步骤。所有位置可识别虚构性质。
2. **真实空数据**：切换真实资料 → 各页出现相应空状态 → 提问不能引用示例，也不能虚构比赛或消息。
3. **真实导入与引用**：导入一份可辨识的材料 → 信息流出现 → 问答检索它 → 点击引用能看到相同原文与来源。
4. **自研采集**：添加 RSS/HTML 来源并采集 → 保存内容、来源与时间 → 再次采集不重复入库 → 禁用后调度不再读取。
5. **有限循环**：模型尝试未知工具、调用超过轮次或超时 → 后端有界停止并展示原因；取消请求可终止继续调用。
6. **模型配置**：保存兼容服务 → 测试成功后回答；无效地址或认证失败得到真实错误；任何读取响应中不出现密钥。
7. **证据边界**：模型返回不存在或跨模式的证据编号 → 拦截或明确剔除并告知缺失依据；不展示为可信引用。
8. **避剧透**：开启设置 → 默认动态、比赛卡和问题建议不泄露演示赛果；主动揭示后才显示复盘。
9. **持久化**：重启服务后设置、资料、来源、已读与关注记录仍然存在。
10. **小屏使用**：窄屏可完整阅读资料、打开设置、发问和停止运行，无横向溢出导致的关键按钮不可用。

## 9. 衡量是否有用

首版先建立可观察记录，不伪造已有用户指标。

| 指标 | 定义 | 初期观察方式 |
| --- | --- | --- |
| 跟队效率 | 用户能否在短时间内说清最近的关键变化 | 小规模任务访谈，记录完成时间与遗漏 |
| 解释可用性 | 用户能否说清比赛观察点及其依据 | 赛前阅读后的复述与反馈 |
| 证据可追溯率 | 回答中的有效引用均能打开对应原文 | 自动检查 ID/模式/来源，再抽样人工核对语义支持 |
| 新内容信噪比 | 新消息中重复、无关和过时内容的占比 | 资料抽样与用户反馈 |
| 正确停止 | 无资料、冲突、模型失败、取消和超限是否被正确处理 | 固定失败场景回归 |
| 持续价值 | 用户是否在下一次比赛前后再次使用 | 用户同意后的小范围试用记录；首版不接第三方埋点 |

## 10. 交付次序

1. 完成本 PRD 与原型规格，确定首版页面与状态。
2. 实现可点击的前端原型，以虚构资料验证主要阅读与交互路径。
3. 接入本地资料、来源采集、配置持久化、自研工具/技能及有限 Agent 循环。
4. 验证模式隔离、密钥、引用、失败和取消边界，并完成桌面/移动视觉检查。
5. 提供运行说明、实际完成范围、验证结果与后续限制。

是否扩大范围，取决于首版的持续跟队体验是否成立。下一阶段先改善来源质量和事件持续跟踪，再考虑更多球队、更深比赛数据与部署方式。
