# 球员肖像匹配实验

日期：2026-10-14。样本是 ESPN `eng.1`、赛季 2026 的三支一线队：阿森纳 29 人、切尔西 30 人、曼城 27 人，共 86 人，阵容里都有出生日期。下面凡是写「实测」的数字都来自这次对公共页面和公开接口的有限访问，不是测试夹具。自动化测试仍用临时数据库和桩，不调用付费模型，也不改用户数据。

身份绑定是唯一过滤器。一个来源可用，仅当能证明是同一名运动员：阵容上的 `provider_id`、出生日期、维基数据 QID，或官网标记里同时出现且两边都唯一的全名和球衣号码。姓名字符串相同不够。

## 结论

**2026-10-15 更正。** 本文档原先的结论是「免费 TheSportsDB 的姓名搜索是失败案例」。那个结论测错了对象：它量的是**姓氏搜索**（`Saka` 会被排序带到 `n'Sakala`）和 `lookup_all_players`（十行字母序、混着教练与别队球员），然后把这个发现下在了整条姓名搜索上。**完整姓名查询是另一个问题**，而且答案很好——详见下面的「2026-10-15 复测」。

现在的默认核对顺序（`PHOTO_SOURCE_ORDER`，最强在前）：

1. `community_name_and_birthdate` — TheSportsDB 完整姓名 + 出生日期到日一致
2. `exact_name_and_number` — 已人工复核的俱乐部官网目录（巴萨、尤文、热刺）
3. `wikidata_espn_provider_id` — 维基数据 `haswbstatement:P3681={provider_id}` + 自由许可 P18
4. 其余社区层（按国籍、出生年、姓氏）
5. `wikimedia_verified_club` → `espn_directory_provider_id` → `espn_provider_id`

社区层内部仍共享一个等级，且**姓氏层不得覆盖全名层**。按 ESPN 编号反查仍然不存在，`lookup_all_players` 仍然不用。已经存下来的社区照片继续由 `apply_cached_portraits` 显示。

**错配 0 例。** 剩余缺口全部核查过，都是真缺口：`Ben White` 库里只有 `Benjamin Whiteman`（1996-06-17，确系另一人）、`Maalik Hashi` 查无此人、`Ceadach O'Neill` 有记录但无 cutout。

同轮修掉一个真实 bug：`_live(record)` 写的是 `record.get("strStatus") in {None, "Active"}`，于是**字段缺失（`None`）通过、字段为空串（`""`）被拒绝**——同一语义两种写法相反结果。TheSportsDB 对大量年轻球员的 `strStatus` 就写空串，`Marli Salmon` 因此被当成退役球员丢掉。已改为「缺失与空串等价，只有明确声明退役才拒绝」。

### 为什么姓氏搜索必须继续退役

同一次复测证实：按姓氏查会被相关度排序带偏（`Saka` → `n'Sakala`，`Rice` → 美式橄榄球运动员 `Jerry Rice Jr.`）。TheSportsDB 的搜索**只返回一条排序后的最佳命中**，所以查询串是否写对就等于结论。姓氏查询问的是一个坏问题，全名查询问的是好问题，两者不能相提并论。

## 原始实验（2026-10-14，结论已更正）

日期：2026-10-14。

以下小节的数字与判断来自当时那轮测量，其中关于「姓名搜索」的结论已被上面的 2026-10-15 复测更正；其余部分（姓氏搜索、`lookup_all_players`、官网探测、维基数据覆盖率）仍然有效。

1. 已经人工复核的俱乐部官网目录：全名和球衣号码在两边都唯一（现有巴萨、尤文、热刺）。
2. 阵容载荷里的 ESPN 头像：只接受路径中的编号与运动员编号一致的那张，不拼 CDN 地址。
3. 维基数据 `haswbstatement:P3681={provider_id}`，条目自己的 P3681 再复述一次，出生日期若两边都写到日则必须一致，P18 只有一张可唯一选定的文件，且共享资源许可已核对。
4. 维基媒体「已核验俱乐部」页作为次级：它仍要先按姓名找到页面，再核对足球运动员、出生日期和现效力俱乐部。弱于编号。
5. TheSportsDB 姓名搜索不再进入默认流程，提供者上的 `portrait` 也不再发出检索。已经存下来的社区照片先留着，等单独的迁移再按证据删。

官网资产在身份清楚时优先于开放图库。曼城官网在 2026-10-14 的静态 HTML 里已经带了可绑定的大名单，适合做成下一份人工复核的提取器，这一次没有接进产品。阿森纳和切尔西这次探测没有得到可绑定的服务端页面。

把模型放进循环里当主动代理，是一等设计选项，不是事后看图的复核。原型在 `server/portrait_agent.py`：模型只发动作，工具只在证明齐全时挂图。它还没有接到对话工具表。`fetch_player_photos` 仍是现在的执行入口，而且不再调用姓名搜索。

## 方法

身份绑定这一路用的是产品里已有的检查，不是另写一套宽松规则：

- `espn_headshot`：载荷提供 `headshot.href`，主机是 `a.espncdn.com`，路径 `/i/headshots/soccer/players/full|thumb/{id}.ext` 里的 id 等于运动员 id。
- 维基数据走已经允许的 `www.wikidata.org/w/api.php`。先 `haswbstatement:P3681=`，`totalhits` 必须是唯一条目，再用 `wbgetclaims` 核对 P3681、P569、P18，然后用现有的共享资源许可检查。没有使用 `query.wikidata.org`。三队合并的 SPARQL 在这台机器上返回 HTTP 429，对方把频率压到每分钟 1 次。
- 社区侧用产品里的匹配器做了一次仿真，只为度量旧路径，不作为新默认。

官网探测只读了少量公开 HTML，不下载球员图片，结果不写入仓库。其他社区站点没有抓取，只按许可、身份键和条款风险排序。

维基百科分类「Arsenal / Chelsea / Manchester City F.C. players」各有 1240、1160、1367 个页面，大约是阵容的四十倍，不能当大名单。未注明日期的 P54（效力俱乐部）会把历史队员算进来，同样不能当当前阵容。

## 官网和其他来源

2026-10-08 的 `server/squad_pages.json` 复核了 96 家俱乐部：43 个页面能在服务端 HTML 里对上至少四分之一的全名，27 家（含阿森纳、切尔西）的服务端 HTML 里没有球员姓名，里尔的图片文件名没有号码和替代文本，因此即使页面验证过也不能当肖像来源。当时已经按「全名且号码两边唯一」接上的只有巴萨、尤文、热刺。

2026-10-14 对三支样本俱乐部又做了有限探测：

- 切尔西。`https://www.chelseafc.com/en` 和两份猜测的球队路径返回 HTTP 500（普通浏览器标识同样失败）。没有可绑定的页面。
- 曼城。`https://www.mancity.com/players/mens` 返回 200，HTML 里嵌了 26 名一线队球员。全名 26 个互不重复，球衣号码 26 个互不重复，26 人都有出生日期，26 人的 `headShotImageUri` 都在 `www.mancity.com`。与 ESPN 阵容全名相交 23 人，这 23 人的出生日期全部一致，冲突 0。对不上的是拼写：Josko / Joško、Kovacic / Kovačić，以及 Allan / Allan Elias。现有的姓名折叠能处理前两对的重音；Allan 与 Allan Elias 不是同一个全名，必须留空。站点上的 `nationality` 不能当身份事实（Erling Haaland 被标成 English）。`optaId` 是另一套编号，不能当成 ESPN `provider_id`。

曼城因此排在「身份已经清楚、值得做一份人工提取器」的位置，而不是「现在就通用爬页面」。提取器必须像现有三家一样写死选择器，并用冻结的 HTML 夹具测试。页面是营销站的内嵌 JSON，字段会变。许可是俱乐部版权，展示必须保留署名，不是自由许可。

没有抓取、只按风险排序的其他来源：

- Transfermarkt、FotMob、Sofascore：条款不接受把它们收成图片源，也没有证明过它们的球员编号等于 ESPN `provider_id`。不接入。
- 付费 API-Football 一类：商业许可，这次没有买来量。除非它给出能对上 `provider_id` 的稳定编号并且许可写明可用，否则不作为下一步。
- 付费 TheSportsDB 密钥：免费层的问题是结果被截断，而且记录上的 `idESPN` 可以是错的。付费如果只是把同一条错误编号的记录返回得更全，并不提高身份强度。不作为下一步。
- OpenFootball、football-data.org、Understat：公开赛程或统计，没有可绑定的球员肖像。

## 新的默认管线

`enrich_player_photos` 的网络顺序现在是：

1. 已配置官网目录（仅 `DIRECTORIES` 里的三家）。
2. ESPN 目录页头像（编号在记录里，沿用原有撤销规则）。
3. 维基数据 P3681。未命中不写到球员行上，好让下一条来源回答。传输失败会写明，并停下这一源的本批。游标按批前进，一批不超过 12 人。
4. 维基媒体已核验俱乐部，只处理仍然没有照片的人。

不调用 `community_portraits.resolve_portrait`。摘要里的 `community_attempted_count` 固定为 0，避免旧的读取方把「缺字段」当成「还在搜姓名」。

已存的社区照片仍可由 `apply_cached_portraits` 显示。同名遮挡的缓存结论仍会把 `namesake_blocked` 抄到行上，验收把它当成 `fix_namesake`，而不是可重试的含糊姓名。整年出生日期不符的拒绝没有放宽。批次上限没有改。

`TheSportsDbProvider.portrait` 直接返回不可重试的缺口，不访问发布方。俱乐部字段的「关系未声明」声明保留，那个值本来就不参与身份判定。

## 迁移

1. 这一次不删除已经存下的社区照片。
2. 下一步迁移只应丢掉这些行：`photo_match` 不是 `community_espn_provider_id` 的社区图，以及保存的 `idESPN` 与阵容 `provider_id` 不一致或为空的完成记录。编号一致的社区图可以留到有更强来源为止，但默认流程不再去找新的。
3. 曼城官网要单独做提取器：冻结一份 HTML，断言全名加号码、拒绝 Allan / Allan Elias 这种全名不等的情况，头像主机只允许 `www.mancity.com`。不要写通用 HTML 猜测器，也不要把 `optaId` 当成 ESPN 编号。
4. 阿森纳、切尔西在出现带姓名和号码的服务端页面之前，继续走维基数据和载荷头像。
5. 不增加 SPARQL，也不为肖像新开主机。
6. 代理叶子要接到 `squad.images` 的工具表时，再暴露 `apply_action`。在那之前，操作规程仍是 `photo_queue` 然后 `fetch_player_photos`。

## 代理叶子

复核方向今天做的是事后判断：代码已经归类，模型在候选集上决定留着、重试还是送去核查，并且不写字段。肖像叶子要的是另一件事。模型是循环里的主动一方：读缺口，点名下一个来源，读工具结果，再决定下一名球员或下一条路径，卡住就带原因停下。

边界：

- 取回和匹配仍由确定性工具完成。证明只认 `provider_id`、出生日期、QID，或已复核目录上的全名加号码。
- 模型不发明照片 URL，不把姓名搜索塞回来，也不推翻同名出生日期拒绝。动作里若带 `photo_url`、`override_namesake`，或放弃时写了词表以外的原因，这一步拒绝，不挂图。
- 工具若返回了与该动作不符的 `photo_match`（例如维基数据动作带回 `community_name_and_birthdate`），同样不挂图。

动作词表：`read_gaps`、`espn_headshot`、`wikidata_p18`、`club_directory`、`wikimedia_club`、`community_idespn`、`give_up`。`club_directory` 只在 `DIRECTORIES` 里有这家俱乐部时才可能挂图，否则返回 `club_site_unconfigured`。`community_idespn` 不发出 `searchplayers.php`，原因码是 `community_name_search_retired`。`give_up` 的原因只能是 `no_identity_proof`、`namesake_blocked`、`source_gap`、`license_not_free`、`club_site_unconfigured`、`stuck`。

和纯确定性管线比：

- 代理有用的地方：多个候选对不上编号时换下一条路径；官网返回「尚未复核」时改去 P3681，而不是猜一张站内图；某条来源传输失败时决定停在这一人还是先做队列里下一个人；卡住时留下词表里的原因，而不是空转姓名搜索。
- 代理必须离开的地方：没有证明就声称这是谁的脸；用模型「看图」推翻生日冲突；从页面文件名或新闻图里猜人；把 Opta 编号当成 ESPN 编号。

计分夹具原在 `tests/test_portrait_agent.py`（测试套件已于 V8.11 移除，需要时 `git show v8.10.0:tests/test_portrait_agent.py`）。一段按菜单行事的脚本处理四个虚构球员：Ben White 的载荷头像因路径编号一致而挂上；Saka 的 P3681 未命中后，俱乐部工具说明阿森纳没有已复核目录，社区编号动作拒绝姓名搜索，然后以 `no_identity_proof` 停下；Reece James 保持 `namesake_blocked`。另一段脚本试图提交 URL、要求推翻同名拒绝、用句子当放弃原因、以及调用词表外的姓名搜索，四步全部拒绝，挂图数为 0。`illegal_attach` 在两段里都是 0。

这是工具面和计分，不是已经接上的对话工具，也没有调用付费模型。接到 `squad.images` 之前，模型读到的规程仍写明：现在能用的是 `photo_queue` 和 `fetch_player_photos`。
