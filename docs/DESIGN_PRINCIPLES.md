# 看台设计原则（重构地基）

本文是 V8 重构的顶层依据。任何新增能力都要能在这里找到对应的原则；与本文冲突的实现应改代码，不改本文。

## 一、定位：信息整合，不是事实认证

看台收集、整理、标注足球信息，不判断真伪。**用户看到的是「谁在什么时候说了什么」，真伪由用户自己判断。**

这条定位推翻了 V7 的核验设计。V7 假设「核验得足够严，输出就可信」，于是把大量机制建立在「这个说法是否成立」上。这是错误的位置：我们既不掌握事实，也没有资格替用户裁决。

正确的信任链是：

```
我们核验过 → 所以可以信           （V7，已废弃）
来源是X、时间是Y、原文在这 → 你自己判断   （V8）
```

## 二、两种过滤必须分开

信息像过滤一样层层整合，但有两种性质完全不同的过滤：

| | 相关性过滤 | 真伪过滤 |
| --- | --- | --- |
| 处理 | 重复、导航垃圾、无关球队、营销内容 | 这条说法的真假 |
| 做法 | **狠命丢** | **一个都不丢，只贴标签** |
| 执行者 | 确定性代码 | 无人执行，交给用户 |
| 理由 | 丢了不损失信息，重跑结果一致 | 丢一条就是替用户下判断 |

V7 的 `verification.py` 把相关性过滤的手法用在了真伪上——它会**删除**未获支持的事实。V8 移除这个动作。

每一层过滤必须满足三条：

1. **只能收窄，不能放宽**——任何一层都不能凭空扩大数据范围。
2. **丢了什么必须看得见**——每层都能回答「这条为什么没进来」，否则无法定位是哪层判错。
3. **可重复**——同样输入跑两次结果一致，否则系统无法调试。

## 三、来源分层：决定说话方式，不决定资格

| 层级 | 含义 | 转述方式 |
| --- | --- | --- |
| `OFFICIAL` | 当事方官方 | 直接陈述 |
| `DATASET` | 结构化数据商 | 直接陈述 + 标注 provider |
| `PRESS` | 有编辑责任的媒体 | 据X报道 |
| `COMMUNITY` | 球迷、社区、个人 | 社区有说法 + 认同量 |
| `DERIVED` | 我们计算得出 | 标注算法与输入 |

**`COMMUNITY` 不是低一等的 `PRESS`。** 它的价值在高时效与现场性：伤情目击、随队见闻、行程线索——这些官方永远不说。它额外携带 `corroboration`（认同量），但：

- 只用于社区源之间排序
- **永不用来提级**（不会因为热度高就变成 PRESS）

这条边界写在代码里，不靠提示词约束模型。

## 四、主张（Claim）与新鲜度

字段级数据形状见 `server/provenance.py`。两个要点：

**两个时间必须分开。** `fetched_at`（我们何时取得）与 `observed_at`（来源何时声明）不是一回事。采集时间不能把旧闻变新。

**TTL 按信息变化速度推导，不是一刀切。**

| 信息 | TTL |
| --- | --- |
| 生日、国籍、身高、照片 | 1 年 |
| 阵容归属、号码 | 赛季中 1 天；转会窗 12 小时；**转会窗最后一周 6 小时** |
| 积分、赛程 | 1 天 |
| 比分、赛果 | 赛后 1 小时 |
| 伤停、首发 | 赛前 48 小时起加速，临近开球 2 小时 |
| 转会传闻 | 12 小时 |

同一个字段在赛季中与赛前 2 小时的新鲜度要求差 24 倍。这是「又快又全」的实现方式：调度器永远知道现在最值得花配额的是哪几项。

## 五、冲突处理

- 值相同 → 合并，保留最强 tier 来源 + 全部来源列表
- **值不同 → 两条都留**，按 tier 排序，界面并列显示
- 永远不自作主张选一个
- **跨 tier 不自动合并**（官网说 183、社区说 185，两件事都该留着）

## 六、权限四层与一条硬线

给 AI 最大权限的前提不是信任，是**把后果关在笼子里**。按「不可逆 × 影响范围」排序：

| 层 | 内容 | 处理 |
| --- | --- | --- |
| 1 | AI 写数据 | **放开**——错了下次刷新覆盖 |
| 2 | AI 写呈现（文字、图表、版面） | **放开**——但须标明 AI 生成，用户可一句话推翻 |
| 3 | AI 改自身行为（技能、策略、调度） | **放开但走提议**——草案 → 评估 → 采纳，不原地改 |
| 4 | AI 改规则（权限、来源白名单、访问范围） | **按住** |

**第 4 层的硬线理由是可审计性，不是信任：** 一个能改写自己约束的系统等于没有约束。你无法回答「它现在的行为是否符合当初的意图」，因为当初的意图已被覆盖。前三层放开之后，这一层是唯一让系统仍可被检查的锚点。

判断某动作只需问：**错了能不能撤回？** 完全可逆的全部放开；不可逆的才需要闸门。

## 七、AI 当作者，不当编译器

让 AI 表达「要什么」，不让它写「怎么做」。

- 要图表 → 输出**图表描述**（哪份数据、什么类型、强调什么、给谁看），由固定渲染器画
- 要界面 → 输出布局意图，不生成前端代码

描述是**数据**：可校验、可缓存、可版本对比、可回滚、坏输入可优雅降级。代码是**行为**：不可测、不可比、一次坏生成整页崩。我们保留设计与安全的最终解释权，AI 拿到呈现方式的全部自由。

## 八、Agent 自主维护

系统的核心不是「一次跑得更好」，而是**持续知道自己知道什么、什么时候该重新确认**。

```
CollectionScheduler（常驻）
  ├─ 优先级队列：什么信息最缺 / 最旧 / 用户最关心
  ├─ 预算闸门：API 配额、并发、域限速
  └─ 每轮产出：新 claim 入库，不直接产出文章
```

**采集与数据存储解耦。** V7 采集的直接产物是新闻稿；V8 的直接产物是结构化 claim 入库，新闻稿只是 claim 的一个视图。这才能「先收全、再组织」。

**决策日志。** 不只存数据，还存「上次为什么这么判断、当时看到什么、后来变了没有」。事后补不回来，必须一开始就有。它支撑三件事：回答「这条多久没确认了」、自我修正、人审。

闭环：**做 → 记 → 看结果 → 提议改 → 验证 → 采纳**。改自己永远走提议，不原地改。

## 九、什么必须有，什么可以等

**现在必须有（结构性，后补会痛到重写）：**

- 主张带来源、时间、层级的数据模型——改它等于改一切
- 按比赛时间推导的新鲜度要求——决定调度器形态
- 决策日志——历史丢了补不回来
- 版本与回滚能力——「放开权限」的前提
- 四层权限边界与那条硬线

**可以等（长在地基之上）：**

- 调度器的复杂优先级策略（先简单轮询）
- AI 生成界面与图表
- 技能自进化
- 多联赛扩展（当前边界：五大联赛 96 队）

判断标准：凡属**数据模型**与**信任链**的，现在做；凡**长在上面**的，等地基稳。

## 十、影响半径

本项目是本地、单用户、不对外发布、无社区账号的系统。**影响半径本来就小，所以这里可以真的放开权限。**

同样的设计放到能发帖、能群发的系统里就不成立。任何新增的对外能力（自动发帖、外部通知）都必须重新评估这一节。
