# V7.4：可以启动、结束并接续的工作

## 页面行为

动态和球队各有独立的“启动／结束”，按球队隔离。点击启动后立即返回状态，后台执行当前一轮；完成后进入等待而非反复调用模型。动态正常每15分钟检查新资料，球队每小时检查；未完成项可缩短下一次检查间隔到5分钟，原有来源冷却和报告有限重试继续生效。

结束会禁止新增、取消本功能当前执行与子任务，并等待清理。完成新闻与有效球队快照保留；不会取消其他球队、另一个功能或独立问答。页面刷新、切换栏目和状态轮询都是只读，不会让已停止的任务复活。

服务重启时，进行中的工作标记中断，不自动重新调用模型。用户点击启动后，系统根据当前来源版本、报告状态和球队组件状态接续。已完成且仍有效的报道不会重新生成；失败稿不自动当成成功。

## 一轮具体做什么

动态先处理本队已存的待整理材料及用户重新启动授权的失败重试，再发现与读取新来源，生成、核对并逐条保存。每份报告都通过通用任务运行器执行，模型请求共用既有调度；同库最多两份报告同时处理。旧失败数量不再作为常驻横幅；展示的是本次工作阶段和可采取行动的错误。

球队通过同一运行器执行可信来源工具，更新阵容、赛程、积分，核心资料保存后补充可核对照片。结构化事实维护不需要每轮再调用模型重写数值；需要解释时由问答助手使用team-information技能读取这些资料。来源暂不可用时保留旧快照并明确状态。

## 系统提示与记忆分层

| 内容 | 管什么 | 保存位置 |
| --- | --- | --- |
| 稳定系统规则 | 工作身份、权限、事实标准、停止与交付原则 | agent_prompts/system.md，结合agent.py任务范围 |
| 技能 | 动态、球队信息、问答的专项流程 | agent_skills三个入口与参考 |
| 工作进度 | 本功能做到哪、累计处理项、当前剩余、错误、下一步 | metadata中的workflow:功能:球队 |
| 可追溯成果 | 已完成报告、来源版本、结构化球队快照、有依据的知识 | reports/evidence/team_snapshots/knowledge等原有记录 |

系统提示词不随每次结果无限增长。模型收到的是本功能、当前球队的少量机器维护计数与固定说明，不复制历史全文，不把存储summary任意文本提升为系统指令。进度记忆永远不是足球事实证据；模型要引用具体内容，仍须重新检查来源权限、版本并实际阅读。

恢复的真正依据是报告/资料记录及其版本，不是模型自己说“已经完成”。提示文件进入应用版本指纹，修改规则后旧进程不会冒充新服务。对话继续保留原来的会话历史和模型绑定，工作进度不混进别人的会话。

## 实现与安全边界

- WorkflowManager拥有启动、等待、停止与重启状态，start幂等，修订号防止旧任务回写覆盖新启动。
- 停止过程由独立清理任务保护，请求断开也继续清理；开始按钮在清理结束前不会创建重叠实例。
- 报告队列支持team_id、owner_id、cancel_event和脱敏进度回调，取得全库执行名额后再原子领取任务，避免全局批次与按队批次双领。
- 公共前端控件处理切队、卸载、GET/POST迟到响应，等待状态仍可结束；已有分页与快照保持可读。
- 新功能不迁移旧数据结构，不批量重写历史成稿，不保存外部原文库。自动化测试只用临时库及模拟执行器。

最终验证：595项Python测试通过（60.105秒），14项前端行为测试及生产构建通过。隔离示例页面实际点击启动/结束、刷新恢复与桌面/窄屏检查通过；真实本机服务从仍在运行的V7.1切换至V7.4前已做数据库和配套key备份，并检查数据库完整性。切换后版本/构建指纹匹配、已有内容可读、工作流默认未启动、没有模型请求被自动发出。未用个人付费模型做自动化验收。
