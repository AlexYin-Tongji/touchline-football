## 0. 一句话结论

用户提的两个问题，根因都已定位并且**用实测证据钉死了**：

1. **球队动态失败**：不是泛泛的「拿不到资料」，而是**一个来源（卫报 The Guardian）在本机网络下完全不可达**，而报告任务被设计成**不允许换来源**，所以直接硬失败。全部 30 次「来源不可读」失败** 100% 都是卫报**，且**根本没有调用模型**（`model_requests=0`）。
2. **球员头像**：`fetch_player_photos` 工具**早就存在且已接线**，但它的数据源里 ESPN 已经死了（403），官方站适配器**只写了巴萨一家**，所以对 96 支球队里的 95 支是空操作。**不需要新建工具，需要换数据源。**

另外发现一个用户没提、但影响所有球队的隐患：卫报是**全部 96 支球队**的配置来源之一。

## 1. 盘点：当前工具系统长什么样（改代码前必读）

### 1.1 工具注册位置

**没有注册表机制**，所有对话工具都在 `server/agent_tools.py` 的一个扁平列表 `TOOL_DEFINITIONS` 里，由 **4 个必须同步的地方**拼装而成：

| 位置 | 作用 |
|---|---|
| `server/agent_tools.py:38-66` | 基础列表字面量（10 个：`team_context`、`search_evidence`、`read_evidence`、`event_timeline`、`match_context`、`discover_news`、`read_article`、`refresh_team_sources`、`use_skill`、`submit_answer`） |
| `server/agent_tools.py:67` | `TOOL_DEFINITIONS.insert(1, {...source_overview...})` — 注意是**插到索引 1**，不是 append |
| `server/agent_tools.py:68-78` | `TOOL_DEFINITIONS.extend([...])` — V7.5 批次，含 `fetch_player_photos`、`get_team_data`、`maintain_team_data`、`research_news`、`compare_sources` 等 |


暴露路径：`LocalTools.__init__`（`agent_tools.py:275-311`）捕获作用域 → `LocalTools.available_tools()`（`agent_tools.py:531-552`）算出 `excluded` 集合 → `server/agent.py:555` 放进 `request_options["tools"]` → `server/provider.py` 转成各家协议格式。

**重要**：决定哪些工具可用的是**作用域（scope）**，不是 skill。见 `agent_tools.py:537-547` 的 6 个 `excluded.update({...})` 分支（由 `mode`/`match`/`report_id`/`allow_network`/`conversation_id` 驱动）。

### 1.2 新增一个工具的**确切**改动点（6 处）

1. **声明** — `agent_tools.py:38-78`。描述用简体中文，结尾带作用域/诚实性限定语。
2. **异步处理分支** — `agent_tools.py:916-1004` 的 `acall`。联网工具必须先调 `self.network_guard()`，在 `self.match or self.run.get("report_id")` 时拒绝，并自增 `self.network_queries`。惰性导入写在分支内，例如 `from .team_center import fetch_player_photos`（`agent_tools.py:927`）。
3. **异步路由集合** — `agent_tools.py:952`：
   ```python
   if name not in {"discover_news", "read_article", "refresh_team_sources", "research_news"}:
       return self.call(name, arguments)
   ```
   **任何新的异步工具如果不加进这个集合，会被路由到同步 `call`，在 `agent_tools.py:914` 抛 `ToolError("未知工具。")`。** 这是最容易踩的坑。
4. **作用域排除** — `agent_tools.py:531-552`。
5. **UI 步骤标签** — `server/agent.py:38-50` 的 `TOOL_LABELS`。漏了不会崩（`agent.py:590` 会退化成 `"unknown"`），但进度条会空白。
6. **能力接口** — 免费。`server/agent.py:35` 在导入时就从 `TOOL_DEFINITIONS` 生成 `CAPABILITIES["tools"]`，`GET /api/capabilities` 自动发布。

### 1.3 schema 校验的两个陷阱（`agent_tools.py:491-529`）

- `type: "integer"` 必须**同时**给 `minimum` 和 `maximum` — 第 521 行无条件读 `rule["minimum"]`/`rule["maximum"]`，缺一个就 `KeyError`。
- `type: "string"` 的 `maxLength` **默认 500**（`rule.get("maxLength", 500)`，第 517 行）。不显式写就会被静默截断到 500 字符。

### 1.4 其他约定

- 参数总大小限制在 `agent_tools.py:1049` 赋值：`submit_answer`/`revise_news` 是 64000，委派工具 24000，**其余 3000**。参数可能超 3000 的新工具必须加进那个三元表达式。
- 错误处理统一：作用域拒绝抛 `ToolError`（`ValueError` 子类，`agent_tools.py:13-14`）；`arun_tool_call`（`agent_tools.py:1044-1060`）统一转成 `{"error": str(exc)}`，刻意用兜底 catch，避免泄漏 provider URL。

`docs/RELIABILITY_V7.md:21` 写「工具共 19 类」，且枚举里**漏了 `fetch_player_photos`**。实际是 20 / 21 / 26。

`LocalTools.run_tool_call()`（`agent_tools.py:1062-1071`）是同步派发器，**无法执行异步工具**。生产代码里**没有调用者**，只有两个测试调用（`tests/test_news_revision.py:103`、`tests/test_tool_reliability.py:121`）。

## 2. 问题一：球队动态为什么老是失败

### 2.1 实测失败分布（可直接复现）

数据源：`data/touchline.sqlite3`，表 `documents`，`collection='runs'`。

```python
# 复现命令

con = sqlite3.connect('file:data/touchline.sqlite3?mode=ro', uri=True)
runs = [json.loads(r[0]) for r in con.execute(
    "select body from documents where collection='runs'")]
print(collections.Counter(r.get('status') for r in runs))
# => Counter({'failed': 76, 'completed': 43, 'cancelled': 4, 'running': 1})   共 124
```

失败的 76 次，错误字符串分布：

| 次数 | 错误串 | 性质 |
|---|---|---|
| 33 | `本地技能文件缺失，无法开始任务。` | **历史问题，已自愈**（全部落在 `2026-09-22T09:07:37Z…09:12:15Z` 这 5 分钟窗口内，见 2.4） |
| **30** | `所选来源暂时都无法读取，请稍后重试；没有使用旧正文或生成未经核对的事实。` | **真正的活跃故障，本文重点** |

| 1 | `收到服务响应，但格式不符合所选接口…` | 模型协议问题，非本主题 |

### 2.2 根因（这是重点，请仔细看）

对那 30 次失败逐条解析 `input_evidence_ids`：

```
队伍分布：  {aston-villa: 24, real-madrid: 6}
来源分布：  {卫报 · 阿斯顿维拉: 8, 卫报 · 皇家马德里: 3}

            model_requests 全部 = 0        ← 关键
            source_read_ms 集中在 8000-8079ms（超时）与 3-70ms（快速失败）
source_errors：全部是同一条占位串「该来源暂时无法读取，未用旧正文替代。」
```

**结论：30 次失败 100% 只涉及一个来源 —— 卫报（The Guardian）。而且一次都没有调用模型，任务在读来源阶段就整体崩了。**

### 2.4 为什么「一个来源坏」会变成「整次任务失败」

这是**设计**导致的，不是 bug，改的时候要小心别破坏安全属性：

1. 报告任务创建时 `allow_network=False`（`server/news_reports.py` 约 719 行）。
2. 因此 `available_tools()` 会**剥掉** `discover_news` / `refresh_team_sources` / `research_news`（`agent_tools.py:539-541`）和 `read_article`（`agent_tools.py:542-543`）。
   → **模型只能反复重读固定的 `input_evidence_ids`，没有任何被允许的替代材料。**
3. 正文**刻意不持久化**：`storage.py:137-139` 设 `body_storage="transient"`，只存在进程内缓存，`BODY_TTL_SECONDS = 20*60`、`BODY_CACHE_BYTES = 4MB`、`BODY_CACHE_ITEMS = 96`（`storage.py:39-41`）。`_hydrate` 在驱逐后返回 `text=""`（`storage.py:141-147`）。
   → 实测：**全部 28 条卫报 evidence 行的 `body_storage` 都是 `transient`，`text` 全为空。** 所以每次重试都必须联网。
4. `server/agent.py:442` 捕获 `(IngestionError, TimeoutError)`，把**真实原因丢弃**，替换成常量串：
   ```python
   return None, {"evidence_id": eid, "message": "该来源暂时无法读取，未用旧正文替代。"}
   ```
5. `server/agent.py:466-467`，当 `selected_evidence` 为空时硬失败：
   ```python
   if not selected_evidence:
       raise AgentFailure("所选来源暂时都无法读取，请稍后重试；没有使用旧正文或生成未经核对的事实。")
   ```

**放大器**：
- `news_reports._snapshot`（`news_reports.py:137-155`）仍会接受「有 `body_hash` 但无 text」的行（正是卫报正文被驱逐后的状态），于是 `enqueue_reports` 持续创建**注定失败**的报告行。
- 自动队列**跳过** `status == 'failed'`（`news_reports.py:700`），手工创建的行带 `manual_stop_after_attempt=True`（`workflows.py:231`），`retry_report` 拒绝重试。净效果：aston-villa 累积 8 条 failed + 3 条 stale，**15/15 失败报告都没有正文**，前端什么都不显示。

**关于 33 次「本地技能文件缺失」**：全部落在 `2026-09-22T09:07:37Z … 09:12:15Z`（已在 DB 中确认窗口）。由 `load_skill` 的 `OSError` 分支在 `agent.py:70` 抛出。四个技能文件**现在都能正常加载**。这不是活跃缺陷，但它会污染任何基于 `output/v75-baseline.json` 的成功率统计（该文件里 `recent_statuses {failed: 52, completed: 34}`）。

### 2.5 次要问题：核验门太刚性（12 次失败）

`_finish` 只在 `run.status=='completed'` **且**（`verification.status=='supported'` 或 `citation_integrity_checked is True`）时才发布（`news_reports.py:571-604`）。当 `verify_submission` 返回 `partial`/`unavailable` 且唯一一次修复机会用尽时，`agent.py:691-702` 抛 `AgentFailure`，**结构完整的草稿被整个丢弃**。声称的安全网 `restore_news_checkpoint`（`agent.py:376-395`）恰恰在失败修复后的状态下会退出。

> 注：`restore_news_checkpoint` 具体是哪个判定条件触发退出，**未验证** — 我未逐行打开 `agent.py:376-395` 确认。

### 2.6 其他静默问题（不会报错，但吞掉能力）

- **反爬页能骗过守卫**。`ingestion.py:608`：
  ```python
  if len(text) < 1500 and re.search(r"checking your browser|just a moment|…", text, re.I):
  ```
  `len(text) < 1500` 这个前置条件意味着**超过 1500 字符的 Cloudflare/同意页完全绕过检测**，随后 `ingestion.py:611` 还会把它标成 `full_text`。没有检查 `cf-mitigated` 头，也没有 consent/region/captcha 模式。
- **ESPN 新闻索引从不缓存失败**。`research.py:537-540` 返回 `[], ["ESPN 新闻：索引暂不可用"], {...}`，`exc` 被绑定却没用。DB 确认：**`espn_news:*` 元数据键为 0 个**，而 `news_index:*` 键有 `last_error`。同时 `collect_team` 请求 `limit=40`（`research.py:776`），导致「extras」路径几乎每轮都触发。
- **JS 渲染的官网只有静态索引**。候选为空时 `_source_index` 抛 `IngestionError("没有发现可读取的文章，页面结构可能已变化。")`（`research.py:407-408`）。DB 里 3 条索引正好是这个串，4 条是 `无法安全读取来源：网络、证书或响应异常`。
- **TyC 条目没有日期**，`within_days` 会在 `max_age_days=7` 下丢弃这些条目。
- **`access_review` 从未被消费**。catalog 里已记录 7 个已知坏站（`restricted`/`access_limited`/`timeout`），每次运行仍然重试。

### 2.7 诊断能力：原因在入库前就被销毁

`agent.py:442` 把所有传输失败压成一个常量串，因此 `run.source_errors` 在不同根因下**字节相同**，而且**任何地方都没有 error code / stage / category 字段**。九种不同的中文「失败」措辞最终落到同一个表格单元格。`output/service-*.log` **只有 uvicorn 访问日志，没有应用错误**，所以 DB 是唯一证据来源。

### 3.2 为什么它现在是空操作

1. **覆盖率 1/96**。`team_portraits.py:22-25` 的 `DIRECTORIES` 里**只有 `barcelona`**。`enrich_portraits`（`team_portraits.py:188`）和 `_apply_directory`（`team_portraits.py:201-202`）对其他队全部提前返回。DB 印证：**5 个快照共 147 名球员，照片数 = 0**。
2. **ESPN 路线已经死了**（我实测）：
   - `site.api.espn.com/apis/site/v2/sports/soccer/eng.1/teams/359/roster` → **HTTP 403**
   - 兜底的公开页面 `www.espn.com/soccer/team/squad/_/id/359/league/eng.1` → **202，空 body，`headshot` 出现 0 次**
   - `a.espncdn.com/i/headshots/soccer/players/full/118426.png` → **HTTP 404**
   - `parse_roster` 读的是 `athlete.get("headshot")`（`team_center.py:164-165`），所以这条路**永远返回空串**。
3. **还有一个静默的「成功」状态**：能解析但没有 headshot 的页面被缓存为 `status='missing'`，而 `_fresh_player_cache` 把它当作**终态保留 86400 秒**（`CACHE_SECONDS`，`team_portraits.py:26`）。`enrich_player_photos` 于是返回 `status='completed'` 配 `missing_count=27` —— 和「ESPN 确实没这个替补的照片」**无法区分**。
4. **有硬上限但没有游标**。`PLAYER_PAGE_LIMIT = 8`、`PLAYER_PAGE_CONCURRENCY = 3`、每文档 22 秒超时（`team_portraits.py:28-30`、`:88`）。候选每次调用都按阵容顺序重算（`team_portraits.py:400-409`），所以 27 人阵容要手动调用 4 次，且**没有续传游标**。
5. **队徽和球队信息对模型不可见**。`team_context` 在 `agent_tools.py:817` 返回固定白名单：
   ```
   ("id","name","english_name","league","league_name","country","city",
    "founded","stadium","nickname","description","official_url","profile_sources")
   ```
   **`crest_url` / `crest_asset_url` / `crest_source_url` / `crest_attribution` / `provider_ids` / `aliases` 全都已存储，但全都对 agent 不可见。** 这一条**零网络开销**就能修。
6. **球队信息字段大面积缺失**。96 行 `teams` 实测：`crest_url` 缺 0、`official_url` 缺 0、`description` 缺 0、`provider_ids` 缺 0；但 **`stadium` 缺 76、`founded` 缺 54、`nickname` 缺 92**。代码里**没有任何地方去抓取或校验它们**，`get_team_data` 只读不写。
7. **没有图片代理**。`server/` 里没有图片路由、没有缩略图器、没有磁盘图片缓存；`/api/*` 被强制 `no-store`（`main.py:426-427`）。所有远端图片都是浏览器热链接，带 `referrerPolicy="no-referrer"`。
8. **没有官网球队信息抓取器**。`research_sources` 的 URL 只用于新闻发现。

### 3.3 可复用的连接键与图片校验

- **球队 id**：`provider_ids.espn` 存的是**球队** id（实测 `barcelona → 83`、`arsenal → 359`）。
- **球员 id**：来自 ESPN 阵容载荷，格式 `id = 'espn-player-<provider_id>'`（`team_center.py:175-182`）。
- **姓名匹配**：官网目录用 `normalized_name()`（NFKD + casefold + 去非字母数字，`team_portraits.py:99-102`）+ 球衣号，并带歧义保护。
- **两套并存的图片校验**（注意是不同的函数）：
  - `_image_url`（`team_center.py:77-90`）较松：任意 `a1-4.espncdn.com` + 图片扩展名。

  - **只有严格的那个在把关缓存照片。**

## 4. 建议的实施方案

> 下面按「先做收益/风险比最高的」排序。每条都标了**改动点**、**风险**、**验收方法**。
> 设计评审（judge panel）**未跑完就被中断**，所以这些是我基于已验证事实给出的建议，不是多模型共识结论。请实施者自行判断。

### P0 — 必修，低风险，直接解掉主故障

#### P0-1 处理死掉的卫报来源

`public/assets/clubs/catalog.json` 中 96 队的 `research_sources` 都含卫报。三种选择，**建议 (b)**：

- (a) **删除**：最干净，但会丢掉一个「理论上应该能用」的多源视角。
- **(b) 降级为「非必需来源」**（推荐）：保留配置，但标记为可失败。核心理由是**即使卫报恢复可达，也不该让单一来源的失败拖垮整次任务**。
- (c) 替换成别的全球源（如已在 `news_sources.py:11` 定义好的 `BBC_HOSTS`、`AS_HOSTS`、`TYC_HOSTS`）。

参考：`server/news_sources.py:31-54` 的 `additional_sources()` 已经是「已评审 feed」的集中声明处，且带有 `reviewed_at` 字段——卫报的处理应该在这里体现，而不是散落在 catalog 里。

#### P0-2 保留真实失败原因（`server/agent.py:442`）

现在是：

```python
except (IngestionError, TimeoutError):
    step("部分来源不可用", "保留已读材料，继续核对可用来源。", "failed")
    return None, {"evidence_id": eid, "message": "该来源暂时无法读取，未用旧正文替代。"}
```

改成把 `str(exc)` 带进 `message`（ingestion 层本身已经会产生**具体的中文错误消息**），并在 `agent.py:466-467` 抛 `AgentFailure` 时把**去重后的具体原因**聚合进去。

**风险：极低。** 这是一行级别的改动，且立刻让下一次失败自解释。
**验收**：存档一条失败报告，确认 `run.source_errors[0]["message"]` 包含真实原因（如超时/403/证书），而不是常量串。

#### P0-3 让报告任务在来源不可读时可以换材料

现在的硬失败在 `agent.py:466-467`。建议：

- 只有当**该事件下确实没有任何可读行**时才硬失败；
- 如果事件里还有可读的其他 evidence，就**基于可读材料出报告**，并附**逐条缺口说明**（哪些来源没读到、为什么）；
- 保持「不得凭空生成未经核对事实」这条底线**不变**。

**风险：中。** 这里最容易把「响亮的失败」偷换成「静默的薄报告」。**必须**在 UI 上明确标注缺口，否则就是退步（见 P1-3 前端提示）。

#### P0-4 正文 TTL 与队列预算不匹配

`BODY_TTL_SECONDS = 20*60`（20 分钟），但报告队列自己的预算是 1800 秒（`agent.py:51`），**TTL 短于队列等待时间**。建议提高 TTL，或对被「排队/正在生成」的报告所引用的 evidence 做**持久化保留**。

### P1 — 应该做，收益明显

#### P1-1 把队徽和球队信息暴露给模型（零网络）

`agent_tools.py:817` 的白名单加入 `crest_url`、`crest_attribution`（以及视需要的 `provider_ids`、`aliases`）。
**风险：极低**，只读字段添加。收益：现在会出现「UI 显示了队徽、但助手描述球队时无法提及队徽」的割裂。

#### P1-2 用 Wikipedia 替换 ESPN 作为球员头像源

**不要新建工具**，改 `server/team_portraits.py` 的数据源层：

- 保留模块骨架：共享文档 worker、per-team/per-player 锁、缓存/重试常量、`_PortraitIdentityError` 逃生口、`enrich_player_photos`/`enrich_portraits`/`apply_cached_portraits` 入口。
- 替换的只是来源层：`DIRECTORIES`、`parse_directory`、`parse_player_portrait`、`_espn_headshot_url`。
- **注意**：`team_center.py` 的 347/353/432/525 行**直接 import 了 `DIRECTORIES`**。新 provider 必须同批改掉，否则这些点会**静默变成空操作**。

**身份校验门（这是设计的关键，不能省）：**

1. summary 的 `description`/`type` 必须表明主体是**足球运动员**，拒绝姓氏消歧页和俱乐部页；
2. `extract` 必须提到**本俱乐部**，复用 `news_sources.py` 已有的别名归一化和「其他俱乐部身份」排除逻辑；
3. **多个合理候选且无法消歧 → 不出图**；
4. extract 无法确定俱乐部时，退回到**一次** Wikidata `wbgetentities` 查 `member-of-sports-team`，**不要**退回到更松的文本匹配。

**诚实性要求（与项目既有原则一致）：**

- 只在能独立验证身份且许可明确时才出图，否则**保留占位符**并说明原因；
- **不要**生成/放大/合成真人脸，**不要**用相似球员的照片顶替；
- 图片来源**不得写入阵容事实**（生日、身高、位置、队伍归属都不能来自 Wikipedia/Wikidata 写入快照）；
- **不要**按姓氏或国籍匹配。已知风险案例：有两个 Emiliano Martínez，必须靠 extract 里的俱乐部名区分。
- 许可校验：建议查 Commons `imageinfo` 的 `extmetadata`（`LicenseShortName`、`Artist`、`AttributionRequired`、`Restrictions`），要求**自由许可**，非自由/合理使用一律拒绝。**许可读不到 = 拒绝**，不是「假定自由」。

**元数据 vs 字节**：建议**只存元数据、热链接字节**（`public/assets/clubs/README.md` 明确把球员头像排除在本项目再分发的范围之外）。新增字段 `photo_license`、`photo_file_page`，与现有 `photo_url`/`photo_credit`/`photo_source_url`/`photo_updated_at`/`photo_match` 并列，并加进 `team_center.py:418` 的白名单和前端 `Player` 类型。

**Wikimedia 限流**：探针中单次匿名 Commons 查询就返回 **HTTP 429**。所以必须走现有的 `research_transport` 请求协调器（共享并发预算），带**描述性 User-Agent**，并且**不要**对 27 名球员做 per-player fan-out。

**验收**：`tests/test_team_portraits.py` 的 27 个测试里，并发/取消相关的那批**应当原样通过**（它们测的是 worker 契约）；ESPN parser 和巴萨目录 parser 的测试需要**重写而不是删除**，因为其中编码的身份不匹配与取消语义是值得保留的部分。新增身份测试：同名球员对、无缩略图页、非足球运动员结果、非本俱乐部、非自由许可文件、许可端点不可用、离线。
